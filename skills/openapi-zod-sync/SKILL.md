# openapi-zod-sync

The `openapi-zod-sync` CLI generates Zod v4 schemas from an OpenAPI spec and checks existing Zod schemas against it. Its JSON report lists each problem with a code, a path and a suggested fix.

**Core rule:** the OpenAPI spec is the contract, unless the user says otherwise. Fix the Zod code to match the spec. Never edit the spec to make a check pass unless the user asks you to.

## Setup

```bash
npm i -D openapi-zod-sync zod   # zod v4 is a peer dependency
npx openapi-zod-sync --help
```

If `openapi-zod-sync.config.ts` exists, read it first. It may already set `spec`, `generate.output`, `check.schemas` and `check.mapping`, so you can leave those out of commands.

## Workflow A — generate schemas

1. List the operations: `npx openapi-zod-sync list <spec> --json`.
2. Choose what to generate from the user's request:
   - one or more endpoints: `--operation getPet,createPet`
   - by tag: `--tag pets`
   - by path glob: `--path '/pets/**'`
   - by method: `--method post`
   - no filter: all operations
3. Run `npx openapi-zod-sync generate <spec> -o src/schemas/api.ts [filters]`. Add `--split-by tag -o src/schemas/` for one file per tag.
4. If the output file already exists and was not generated, stop and ask before overwriting it. A generated file starts with `// Generated by openapi-zod-sync`.
5. Confirm with `npx openapi-zod-sync check <spec> -s <output> --format json`. Expect 0 errors and 0 warnings.

## Workflow B — check and fix drift

1. Run `npx openapi-zod-sync check <spec> -s 'src/**/*.ts' --format json`. Exit code 1 means drift above `--fail-on` (default `error`). Exit code 2 means a usage or loading error: read stderr.
2. For each `results[]` entry with `status: "drift"`, open `match.file` and edit the export named in `match.export`. Each issue has `path` (the field inside the schema, e.g. `items[].owner.email`), `expected` and `actual`, and a `suggestion` with the exact Zod change.
3. Keep the user's style. Edit the existing schema in place, keep their names, helpers and composition (`.extend`, `.omit`, shared sub-schemas). Don't replace a hand-written file with generated code.
4. Re-run `check` until the drift you were asked to fix is gone. Report what changed and what is left.

## Reading the report

| Code | Meaning | Usual fix |
| --- | --- | --- |
| `MISSING_FIELD` | Field in the spec, absent in Zod | Add the field (see `suggestion`) |
| `EXTRA_FIELD` | Field in Zod, absent in the spec, or readOnly/writeOnly in the wrong direction | Remove it, or `.omit()` it for that direction |
| `TYPE_MISMATCH` | Different type, or union vs single type | Change the Zod type |
| `OPTIONALITY_MISMATCH` | required vs `.optional()` | Add or remove `.optional()` |
| `NULLABILITY_MISMATCH` | null allowed on one side only | Add or remove `.nullable()` |
| `ENUM_MISMATCH` | Different enum values | Align the `z.enum([...])` values |
| `FORMAT_MISMATCH` | email/uuid/date-time… differs | Use `z.email()`, `z.uuid()`, `z.iso.datetime({ offset: true })`… |
| `CONSTRAINT_MISMATCH` | min/max/pattern/multipleOf/uniqueItems differ | Use the bound from `expected` |
| `MISSING_SCHEMA` | No Zod export found for an operation part | Generate it, or map an existing export (below) |
| `UNCOMPARABLE` | Zod accepts anything there (`z.any`, a transform) | Usually leave it and mention it to the user |

What the severity tells you:

- `error`: Zod rejects data that the contract allows, or the structure differs. Fix these first.
- `warning`: Zod accepts data that the contract forbids.

`status: "covered"` means the operation part is a plain `$ref` to a component that is already checked. Nothing to do.

## Matching Zod exports to the spec

The checker pairs exports with operation parts in this order:

1. **Mapping in the config:** `check.mapping: { 'createPet.body': 'NewPetSchema', '#/components/schemas/Pet': 'PetSchema' }`. Use `file.ts#Name` when the same name exists in several files.
2. **Metadata:** `.meta({ openapi: { operationId: 'createPet', part: 'body' } })`. Parts are `params`, `query`, `headers`, `body` and `response.<status>`.
3. **Naming convention:**
   - operation parts: `CreatePetBody`, `ListPetsQuery`, `GetPetParams`, `ListPetsHeaders`, `GetPetResponse200`, `GetPetResponseDefault`
   - components: `Pet` / `PetSchema`, with `PetInput` for the request variant

If `MISSING_SCHEMA` lists a schema that does exist under another name, add a mapping instead of renaming the user's export.

## Common mistakes

- Running `generate` over a hand-written file. Generate into a new file, or edit in place.
- Changing `openapi.yaml` to silence drift. Ask the user which side is the source of truth.
- Using `z.coerce.boolean()` for query booleans: it turns `"false"` into `true`. Use `z.stringbool()`, which is what the generator emits.
- Comparing a request body that still includes `readOnly` fields such as `id`. Use `.omit({ id: true })` for the request schema.
- Treating `--fail-on never` as a fix. It only changes the exit code.

## CI

```bash
npx openapi-zod-sync check --format markdown --out sync-report.md --fail-on error
```

Security: `check` imports and runs the schema modules it is given, so only point it at trusted code. Add `--no-remote-refs` when the spec comes from an untrusted source.
